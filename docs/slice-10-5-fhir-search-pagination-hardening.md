# Slice 10.5 - FHIR Search, Pagination and Interoperability Hardening

## Purpose

Slice 10.5 hardens the existing CarePoint FHIR R4 read-only facade by adding patient-scoped search and deterministic pagination to resources whose authorization model is already implemented in the CarePoint domain.

This slice does not broaden clinical access. FHIR search reuses the same CarePoint authorization and patient-release rules used by the native APIs.

## Capability version

`CapabilityStatement.software.version = slice-10.5`

The CapabilityStatement advertises search-type support for:

- `Appointment`
- `DiagnosticReport`
- `DocumentReference`

`ImagingStudy` remains read-only by id in this slice because the current PACS abstraction does not yet expose a complete, queryable study catalogue with series/instance metadata.

## Search endpoints

### Appointment

`GET /api/v1/fhir/R4/Appointment`

Supported parameters:

- `patient` - required Patient reference or raw CarePoint patient id
- `status` - optional comma-separated FHIR Appointment status tokens
- `_count` - optional page size, default 20, maximum 100
- `_offset` - CarePoint pagination control, default 0

The underlying Slice 10 Appointment authorization remains authoritative. A patient cannot use pagination to enumerate another patient's appointments.

### DiagnosticReport

`GET /api/v1/fhir/R4/DiagnosticReport`

Supported parameters:

- `patient` - required Patient reference or raw id
- `status` - optional comma-separated FHIR DiagnosticReport status tokens
- `_count`
- `_offset`

Patient accounts only search diagnostic reports already released to that patient. Provider searches continue to use the existing document/report treatment-relationship, consent and authorship rules.

### DocumentReference

`GET /api/v1/fhir/R4/DocumentReference`

Supported parameters:

- `patient` - required Patient reference or raw id
- `status` - optional FHIR DocumentReference status token
- `_count`
- `_offset`

Patient accounts only see documents with `releasedToPatient = true`. External imaging references still do not expose PACS URLs through FHIR.

## Pagination

Search results are FHIR `Bundle` resources with:

- `type = searchset`
- exact `total` within the authorized source window
- page-specific `entry`
- `self` link
- `next` link when more results exist
- `previous` link when the current offset is greater than zero

`_count` must be an integer from 1 through 100.

`_offset` must be a non-negative integer and is bounded by the interoperability layer.

The current CarePoint domain list APIs have defensive source windows of 200 Appointments and 500 clinical documents/reports. Slice 10.5 deliberately fails closed with HTTP 409 if one of those windows is saturated. It does not publish a misleading `Bundle.total` when the underlying domain API cannot prove the exact total.

A later slice can replace this safeguard with native server-side cursor pagination in the domain services.

## Search parameter hardening

Only explicitly implemented parameters are accepted.

Examples that return `400 OperationOutcome`:

- unknown search parameters
- repeated scalar parameters
- `_count` larger than 100
- negative or non-integer pagination values
- unsupported status tokens
- token-system syntax not implemented by the current facade

This prevents clients from assuming silently ignored FHIR search behavior.

## Authorization behavior

### Appointment

The existing Appointment search authorization remains unchanged. The FHIR pagination layer operates only on the already-authorized result set.

### DiagnosticReport and DocumentReference

The FHIR layer obtains the patient-scoped collection through `DocumentsService` before pagination.

For patient accounts:

- the authenticated patient's CarePoint patient id must equal the requested FHIR patient reference
- document release gates remain mandatory
- diagnostic report release gates remain mandatory

For providers:

- active-provider validation remains mandatory
- treatment relationship / patient consent / authorship rules remain authoritative
- FHIR does not bypass encrypted document/report presentation or attestation verification

## Response security hardening

FHIR controller responses now include:

- `Cache-Control: private, no-store, max-age=0`
- `Pragma: no-cache`
- `X-Content-Type-Options: nosniff`
- `Vary: Authorization`

The same protection is applied to FHIR `OperationOutcome` error responses generated by the FHIR exception filter.

## Audit events

Slice 10.5 adds FHIR-specific search audit events including pagination metadata and authorized access basis where applicable:

- `FHIR_APPOINTMENT_PAGED_SEARCH`
- `FHIR_DIAGNOSTIC_REPORT_SEARCH`
- `FHIR_DOCUMENT_REFERENCE_SEARCH`
- denied cross-patient FHIR document/report search events

## Validation

The dedicated Slice 10.5 smoke test verifies:

- CapabilityStatement version and search declarations
- Appointment pagination with self/next/previous links
- Appointment status filtering
- DiagnosticReport pagination
- DocumentReference pagination
- patient release semantics
- cross-patient denial
- invalid `_count`
- unsupported search parameters
- invalid status tokens
- no-store / no-cache / nosniff headers on successful and error responses

The Slice 10 workflow continues to execute the cumulative Slice 10, Slice 10.3, Slice 10.4 and Slice 10.5 interoperability smoke tests.

## Non-goals

Slice 10.5 does not implement:

- arbitrary FHIR search parameters
- FHIR `_include` / `_revinclude`
- `_sort`
- `_elements`
- `_summary`
- conditional reads
- history interactions
- batch or transaction Bundles
- write/create/update/delete FHIR interactions
- PACS-wide ImagingStudy search
- full SMART-on-FHIR authorization

Unsupported behavior is rejected rather than silently approximated.

## Suggested next increment

Slice 10.6 should focus on interoperability identity and authorization hardening: SMART-on-FHIR discovery metadata, OAuth scope mapping and standards-aligned external client authorization without weakening the existing CarePoint session and clinical access controls.
